别再背 IP：管好多台机器，也让 Codex 别跑错片场

我本机 SSH 配置里有 homelab、debian-dell、pvenode 等真实别名。这里讲讲它们怎么帮我省脑子，以及怎么把同一套规则交给 AI。

2026-08-09Shubo8 min

机器少的时候，管理服务器靠记忆完全没问题。一台云主机、一个端口、一把密钥，输几次就记住了。后来机器多起来，我发现自己每次连接前都在做一道不该存在的选择题：这个 IP 是家里的机器，还是那台 VPS？端口是默认的，还是我三个月前改过的那个？

再后来我开始让 Codex 帮忙查服务。人记错 IP 最多连错一次，AI 拿到一句“去服务器上看一下”，有可能非常勤快地在错误的机器上把整套排查流程跑完。效率很高，方向完全不对。

我现在的做法不复杂：SSH alias 负责给机器起稳定的名字，shell alias 负责缩短常用动作，任务说明负责告诉 Codex 去哪里、在哪个目录、能做什么。三件事分开以后，脑子终于不用兼职做 DNS。

先给每台机器一个能看懂的名字

我的 ~/.ssh/config 里现在有 homelab、debian-dell、debian-dell-lan、pvenode、pvenode-ssh 等别名。下面的字段都做了脱敏，但 Host 名是我实际在用的。

Host homelab
    HostName <REDACTED_HOST>
    User <REDACTED_USER>
    Port <REDACTED_PORT>
    IdentityFile ~/.ssh/<REDACTED_KEY>
    ServerAliveInterval 30
    ServerAliveCountMax 3

有了这段配置，连接命令就从一长串参数变成了：

ssh homelab

这个变化看着只是少打几个字，真正的价值是把“怎么连接”和“连哪台机器”拆开了。主机地址、端口、用户和密钥以后发生变化，我只改配置，日常命令、脚本和给 Codex 的任务描述都不用跟着改。

别名最好按机器的角色取，而不是按 IP 尾号取。homelab 至少还能提醒我这是家里的服务节点；server-110 只会提醒我，当初起名时已经放弃思考。

同一台机器有两条路，就把路写进名字

debian-dell 和 debian-dell-lan 实际上指向同一台机器，但用途不同：前者是日常使用的远程连接路径，后者保留为局域网直连。外面的路出问题时，我在家里还能走 LAN，不至于为了修隧道先把自己锁在门外。

Host debian-dell
    HostName <REDACTED_EXTERNAL_HOST>
    User <REDACTED_USER>
    IdentityFile ~/.ssh/<REDACTED_KEY>
    ProxyCommand <REDACTED_PROXY_COMMAND>

Host debian-dell-lan
    HostName <REDACTED_LAN_IP>
    User <REDACTED_USER>
    IdentityFile ~/.ssh/<REDACTED_KEY>

我在 PVE 相关机器上也用了类似的命名：pve-debian13、pve-debian13-cf、pve-debian13-frp。基础名表示机器，后缀表示连接路径。看到命令就知道走的是哪条路，排查时不用靠猜。

这里有个小原则：默认别名应该指向平时最稳、最常用的路径；带后缀的别名留给局域网、代理、隧道或救援路径。否则每次执行 ssh host 之前还要回忆“这个默认到底默认了什么”，别名就算白起了。

跨机器共享 alias，我会把“方便”和“秘密”分开

SSH 配置里真正不能到处同步的是私钥。主机名、用户名和网络拓扑虽然通常不算密钥，也属于不该随手公开的基础设施信息。所以我不会把整个 ~/.ssh 扔进 Git，然后安慰自己仓库是 private。

如果要在 Mac、笔记本和管理机之间共享，我更愿意拆成下面这样：

~/.ssh/config
~/.ssh/config.d/
├── 00-shared.conf       # 通用选项和统一的 Host 命名
└── 90-local.conf        # 当前机器的地址、用户、密钥和代理

~/dotfiles/shell/
├── aliases.shared.zsh   # 各台机器都能用
├── aliases.macos.zsh    # 只给 macOS
└── aliases.linux.zsh    # 只给 Linux

主配置只负责 Include：

Include ~/.ssh/config.d/*.conf

aliases.shared.zsh 里放不含秘密的快捷命令，例如：

alias h='ssh homelab'
alias dell='ssh debian-dell'
alias dell-lan='ssh debian-dell-lan'
alias pve='ssh pvenode'

alias gs='git status --short --branch'
alias gl='git log --oneline --decorate -12'

共享文件可以进自己的 dotfiles 仓库，本机连接细节放在忽略列表里。真要同步完整连接配置，也应该先加密；私钥则继续使用密码管理器、安全拷贝或硬件密钥处理。Git 历史很长，长到足够记住每一次“我晚点再删”。

Shell 启动时按系统加载：

source ~/dotfiles/shell/aliases.shared.zsh

case "$(uname -s)" in
  Darwin) source ~/dotfiles/shell/aliases.macos.zsh ;;
  Linux)  source ~/dotfiles/shell/aliases.linux.zsh ;;
esac

简单 alias 适合固定命令；需要接收参数、做判断时就写 shell function。不要把一段八十字符的管道伪装成 alias，然后半年后没人敢碰，包括当初写它的自己。

让 Codex 去指定机器，别只说“去服务器看看”

Codex 在本地仓库里启动，并不会自动知道我要操作哪台远端机器。我的任务描述至少会写四件事：目标 SSH alias、远端工作目录、第一组只读检查、允许修改的范围。

例如，我要它去 homelab 检查一个项目，会直接这样说：

目标机器：homelab
远端目录：<REMOTE_PROJECT_DIR>

先执行并报告：
1. hostname
2. pwd
3. git status --short --branch
4. git rev-parse HEAD

只操作 homelab，不要连接其他机器。
先做只读检查；需要修改或重启服务时，再按任务范围继续。

第一条远程命令通常也很朴素：

ssh homelab '
  cd <REMOTE_PROJECT_DIR> &&
  hostname &&
  pwd &&
  git status --short --branch &&
  git rev-parse HEAD
'

这几行会同时证明三件事：连的是哪台机器、站在哪个目录、代码目前是什么状态。后面即使要部署，也先有一张清楚的起点照片。否则最后看到服务返回 200，只能证明某个地方有东西活着，不能证明你刚改的版本真的在那里。

把机器路由写进 AGENTS.md

如果一个仓库经常需要跨机器操作，我会在项目的 AGENTS.md 里放一段很短的路由说明。这里同样只写 alias 和职责，不写地址、密码或密钥：

## Machine routing

- homelab: personal services; read-only checks by default.
- debian-dell: default route to the remote workstation.
- debian-dell-lan: LAN rescue route for the same workstation.
- pvenode: virtualization host; do not mutate without explicit scope.

For every remote task:
1. print hostname, pwd, branch and HEAD first;
2. stay inside the named remote directory;
3. never fan out to another host unless requested.

这样做的好处不是让 AI “更聪明”，而是减少它需要猜的东西。alias 解决机器身份，目录解决操作边界，分支和 SHA 解决版本身份。提示词不用写得像合同，但关键坐标得有。

改配置以后，先解析，再连接

新增或调整 SSH alias 后，我会先用 ssh -G 看 OpenSSH 最终解析出的配置。它不会发起连接，适合检查旧配置是否抢先匹配、IdentityFile 有没有用错、ProxyCommand 是否真的生效。

ssh -G debian-dell
ssh -G debian-dell-lan
这两个命令的输出可能包含真实主机名、用户名、密钥路径和代理配置。自己检查没问题，截图、发帖或粘给第三方前要脱敏。本文只公开了 Host alias。

解析正确以后再做一次实际连接。对于重要机器，我还会确认公钥登录成功，并明确测试密码登录被拒绝。能连上只是半张答卷；不该用的方式连不上，才是另一半。

我踩过的几个小坑

第一，同一个 alias 在不同电脑上指向不同机器。这个问题看起来很蠢，出现场景却很多，尤其是手工复制配置以后。共享 Host 命名就是为了避免这种分叉。

第二，只同步 shell alias，不同步 SSH Host。结果 alias h='ssh homelab' 在新电脑上存在，homelab 却不存在。快捷方式很完整，路没铺。

第三，把“去生产看一下”交给 Codex，却不写 alias 和目录。它可能先花时间找机器，也可能根据上下文选一台看起来最像的。AI 的主动性在这里不是优点，跟出租车司机主动给你换目的地差不多。

第四，为了省事，把私钥也塞进 dotfiles。这个不叫自动化，叫自动扩散。共享配置和共享凭据是两件事，最好永远别合并。

最后留一份最小规则

如果只记住几条，我会留这五条：用角色命名机器；同机不同路径加后缀；共享 alias，不公开连接细节；远程任务先报 hostname、cwd、branch 和 SHA；给 Codex 的每个任务都写清目标 alias 与目录。

这些东西不会让家里的机器变少，也不会让 SSH 变得更酷。它只是把“我应该知道自己在哪”从记忆题变成配置题。机器一多，这点朴素的确定性非常值钱。
